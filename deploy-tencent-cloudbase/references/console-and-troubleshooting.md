# 控制台操作与排障

2026-10-13核对官方资料。下面是语义步骤；不要固定 AX 索引、截图坐标、菜单文案或闲置时长。

## 控制台发布

1. 在用户指定的已登录会话核对环境及服务。选择新服务还是更新已有服务，应由用户目标与现有业务决定。
2. 对首次启用云托管，读启用页的条款/费用提示，交用户完成接受操作；不把查看说明当成同意购买。
3. 选择支持的源码包、仓库或镜像方式。源码 ZIP 的根目录和 Dockerfile 构建上下文匹配；核对端口与运行时变量。检查继承配置，更新服务不代表变量、网络或扩缩容一定保持原值。
4. 提交前核对具体服务、发布内容、访问策略和费用相关变更。提交后保留版本和任务标识，观察构建与启动；不要用重复提交处理日志面板空白。
5. 就绪后到生效版本/流量配置核查目标版本实际承接情况。若完整替换却仍由旧版100%承接，切换至目标版本并再核对；若使用“回退”入口，按对话框目标版本确认其实际语义。
6. 公网读到新版本内容、核心路径成功后才完成。按需保留脱敏的版本状态、资源指纹与结果；不拍展开的密钥字段。

## 有界观察

开始时给当前阶段设截止时间，参考平台任务上限和项目构建规模。可从30–60秒检查间隔开始，未变时退避；单次等待不要阻止必要的用户沟通。构建耗时不是失败依据。

到期仍处理中：重新核对任务状态，区分构建、拉镜像、启动和健康检查，读该阶段日志。没有可定位错误则报告仍在处理及证据，不盲目再发一版。若日志面板空白，先刷新或重新进入同一任务；界面树可能滞后于截图，读取新状态后再行动。认证/额度/平台异常无法在授权范围解决时说明所需协助。

## 常见差异

| 现象 | 下一项核查 |
| --- | --- |
| 新版正常，页面仍旧 | 先读实际流量权重，再比较公网资源指纹；随后查入口URL、缓存或代理。不要默认归咎缓存。 |
| 构建成功但实例启动失败 | 启动日志、Linux依赖、入口命令、监听地址/端口、健康检查、内存及外部连接。 |
| 本机Docker运行不了 | CLI存在不代表守护进程运行。记录本机镜像未验；可在授权范围内用云构建验证Linux运行，不能把本机Node构建当容器验收。 |
| 前端可以访问，API拒绝 | 平台网关/服务鉴权与应用鉴权分别检查；再查同源、代理TLS、Cookie和请求路径。不要直接关鉴权。 |
| 微信只显示认证文字 | 核对是否HTTP Basic 401及WWW-Authenticate；普通表单和会话须真实测试。不要泄露诊断凭据或自动降低认证要求。 |
| 默认域名显示访问提示/下载 | 检查平台中间页或Content-Disposition；它与应用口令及浏览器证书警告不同。正式入口用符合要求的自定义域名，不规避限制。 |
| 依赖/模型下载失败 | 确认构建容器的网络、包版本与架构；运行时离线需要时可在镜像构建期准备模型，权衡体积与冷启动。不用私钥或禁TLS绕过。 |

## CLI/API 路径

优先已有且适合目标的官方工具。不为部署复制浏览器Cookie到CLI，也不把账户密钥存入技能。先查看已安装版本的帮助，明确环境、服务、源码上下文与端口；支持dry-run时可用其预检，但它不证明真正发布可用。不要默认使用 `--force` 或 `--yes`。

当前CLI文档有 `tcb cloudrun deploy`，并区分灰度/等待等选项；每次执行以实际版本为准。注意 `tcb cloudrun run` 的当前文档限定函数型服务，不能用它代替容器镜像实测。API方式同样分别核对任务、版本和流量。
